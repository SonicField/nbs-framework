**Architecture: Layered Heuristic Pipeline**

The solver should be structured as a pipeline where each stage improves the previous result:

```
Input (city coordinates) → Construction → Improvement → Output (tour + cost)
```

**Stage 1: Construction heuristic (produces initial tour)**
- Nearest-neighbour: O(n²), simple, produces a tour typically 20-25% above optimal
- Greedy edge insertion: O(n² log n), often better starting point
- Recommendation: implement nearest-neighbour first, greedy as stretch goal

**Stage 2: Local search improvement**
- 2-opt: O(n²) per pass, repeatedly removes two edges and reconnects if shorter. Multiple passes until no improvement found. This is the workhorse.
- Or-opt (moving segments): complementary to 2-opt, catches improvements 2-opt misses
- Recommendation: 2-opt is essential. Or-opt is a strong second.

**Stage 3 (stretch): Christofides-inspired**
- Full Christofides requires minimum spanning tree + minimum weight perfect matching. The matching step is complex (Edmonds' blossom algorithm). For a practical C program, a greedy matching approximation is more realistic.
- This gives provable 3/2-approximation for metric TSP.

**Data structures:**
```
typedef struct { double x, y; } City;
typedef struct { int *tour; int n; double cost; } Solution;
```

**Key invariants the implementation must preserve:**
1. Tour is a permutation of [0, n-1] — every city visited exactly once
2. Tour cost equals sum of consecutive edge weights (including return to start)
3. Improvement steps must never increase total cost (monotonic improvement)
4. Distance function must satisfy triangle inequality for metric TSP guarantees

**Falsification — what would show the solver is wrong:**
- A tour that visits a city twice or skips one (invariant 1 violated)
- Reported cost differs from recalculated cost (invariant 2 violated)
- 2-opt produces a tour worse than its input (invariant 3 violated)
- Output tour is worse than nearest-neighbour alone (improvement stage is harmful)

**File structure recommendation:**
- `tsp.h` — types, constants, function declarations
- `tsp_io.c` — reading input, writing output
- `tsp_construct.c` — construction heuristics
- `tsp_improve.c` — 2-opt and local search
- `tsp_main.c` — main driver, argument parsing
- `tsp_test.c` — test harness with known instances
- `Makefile` — build with ASan/UBSan targets per engineering standards

**Survey: Polynomial-Time Exact TSP — Theoretical Landscape**

**1. Special cases where exact poly-time TSP is known:**

- **TSP on graphs with bounded treewidth**: If the underlying graph has treewidth k, TSP can be solved in O(n * 2^k * k) via dynamic programming. For fixed k this is polynomial in n. But general TSP has unbounded treewidth (complete graph on n vertices has treewidth n-1). This does not help for the general case.

- **TSP on Halin graphs**: Exact polynomial solution exists (Cornuejols, Naddef, Pulleyblank, 1985). Halin graphs are a specific graph class (tree plus a cycle connecting leaves). Not general.

- **TSP on series-parallel graphs**: Solvable in polynomial time. Again, a restricted graph class.

- **TSP with at most k distinct edge weights**: For fixed k, solvable in polynomial time. But general Euclidean TSP has n(n-1)/2 distinct distances typically.

- **Shortest Hamiltonian path on interval graphs**: Polynomial. Very restricted.

**2. Near-misses and structural observations:**

- **LP relaxation (Subtour elimination)**: The Held-Karp LP relaxation of TSP is solvable in polynomial time (via the ellipsoid method or cutting planes). It gives a lower bound within a factor of 4/3 of optimal for metric TSP (conjectured to be within a factor of 1 + epsilon). But *rounding* the LP solution to an integer tour is where NP-hardness bites. The LP itself is poly-time; the integrality gap is the barrier.

- **Christofides-Serdyukov (1976/1978)**: 3/2-approximation for metric TSP. This stood as the best known ratio for 45 years until Karlin, Klein, and Oveis Gharan (2021) achieved (3/2 - epsilon) for some small epsilon. Still approximation, not exact.

- **TSP polytope structure**: The convex hull of tours is well-studied. We know many valid facet-defining inequalities (subtour elimination, comb inequalities, clique tree inequalities). But a complete description of the TSP polytope would require exponentially many facets (unless P=NP), which is why cutting-plane methods cannot be guaranteed polynomial.

**3. Barriers to a polynomial exact algorithm:**

- **NP-completeness (Karp 1972)**: TSP decision version is NP-complete. A poly-time exact solver implies P=NP.

- **Barrier results against P=NP proofs**: Baker-Gill-Solovay (relativisation), Razborov-Rudich (natural proofs), Aaronson-Wigderson (algebrisation) — these show that standard proof techniques cannot resolve P vs NP either way. This means we cannot prove it impossible using known methods, but also that any solution would require fundamentally new mathematical ideas.

- **Circuit complexity lower bounds**: We cannot even prove that TSP requires super-linear circuits. The gap between what we can prove and what we believe is enormous.

**4. Honest assessment of exploitable angles:**

The special cases share a common property: they all restrict the graph structure to something with bounded combinatorial complexity (treewidth, planarity, series-parallel decomposition). General Euclidean TSP on n points in the plane has none of these structural restrictions.

The LP relaxation angle is the most tantalizing — we can solve the relaxation in poly time, and the integrality gap appears small empirically. But closing the integrality gap (rounding to an exact integer tour) is equivalent to solving TSP exactly, which is the original problem.

**5. What would falsify my pessimism:**

- A polynomial-time rounding scheme that preserves optimality for the Held-Karp LP relaxation
- A polynomial-time algorithm for Hamiltonian cycle (a sub-problem of TSP, also NP-complete)
- A proof that some structural property of Euclidean distance matrices makes Euclidean TSP fundamentally easier than general TSP (note: Euclidean TSP is still NP-hard, proved by Papadimitriou 1977)
- Any resolution of P vs NP

**Bottom line**: Every known poly-time exact result for TSP requires restricting the input to a graph class with bounded combinatorial complexity. General TSP (including Euclidean TSP) has no such restriction. The LP relaxation is the closest thing to a 'near miss,' but the rounding barrier is exactly where NP-hardness lives.

For each inner layer, you need to decide where each point gets inserted into the growing tour. The problem is that the optimal insertion of layer i depends on the insertion of layer i+1 (and deeper layers), because inner points change the tour geometry and affect which insertions are locally optimal.

**Concrete counterexample to the DP premise**: Suppose the outer hull has 4 points (a square), and there are 4 inner points. Where you insert inner point A affects the cost of inserting inner point B, because the tour edge that B would be inserted into changes depending on A's placement. This creates interdependence that requires considering all combinations of insertions — which is exponential in the number of inner points.

This is essentially a variant of the *sequence-dependent insertion problem*, which is itself NP-hard.

**However**: there is a related result worth knowing. For the case where ALL points lie on a constant number of nested convex layers (i.e., k = O(1)), there IS a polynomial-time exact algorithm. This is because the DP state space is bounded by the layer structure. But for general point sets, k can be O(n) (worst case: spiral arrangement), so this does not give a general polynomial algorithm.

**Verdict**: The hull layering idea has a real kernel of truth (it works for bounded k) but does not generalise. Not worth prototyping as a general solver — it will fail on instances with many layers. The Held-Karp bound is a better use of engineering time.

**Non-graph-theory approaches to TSP:**

**1. Topology: TSP as a problem in the configuration space of loops**

The set of all closed curves through n points in the plane forms a topological space. The optimal tour is a point in this space that minimises a functional (total length). This is formally a problem in the *calculus of variations* — finding the curve that minimises an energy functional.

In continuous settings, gradient flow on loop space converges to local minima. Our 2-opt is essentially a discrete analogue of this. The question: does the topology of the loop space for Euclidean TSP guarantee a unique local minimum (which would then be global)? If so, any gradient descent method would find the optimum.

**Falsification**: Find a Euclidean instance where 2-opt converges to different tours from different starting points. We already know this happens — so the loop space has multiple local minima. This angle fails in its naive form. BUT: the right gradient flow in the right topology might still avoid local minima (cf. convexification techniques in optimisation).

**2. Higher-dimensional embedding: lift and project**

Embed the 2D point configuration into a higher-dimensional space where the TSP polytope becomes simpler. This is the *extended formulation* approach.

Known result: Yannakakis (1991) proved that the TSP polytope requires exponentially many facets in ANY symmetric extended formulation. Fiorini et al. (2015) extended this to ALL extended formulations (symmetric or not). This means there is no polynomial-size linear program for TSP, regardless of how many dimensions you embed into.

**This is a hard barrier.** Lifting to higher dimensions does not help if you stay within linear programming. HOWEVER — this does not rule out *nonlinear* formulations in higher dimensions.

**3. Algebraic geometry: TSP as a system of polynomial equations**

Encode TSP as finding the zeros of a system of polynomial equations (each city must be visited once, minimise total distance). Tools from algebraic geometry (Grobner bases, homotopy continuation) can solve polynomial systems.

Problem: the degree of the system grows with n, and Grobner basis computation is doubly-exponential in the worst case. Not polynomial.

The point cloud defines a filtration of simplicial complexes (Vietoris-Rips, Cech). The persistent homology of this filtration captures multi-scale geometric structure that distances alone do not.

Wild speculation: the optimal tour might be recoverable from the 1-dimensional persistent homology (which captures loop structure). At the filtration parameter where the single dominant H1 generator appears, the corresponding 1-cycle might approximate the optimal tour.

**This is testable.** Compute the Vietoris-Rips persistent homology, extract the 1-cycle at the critical filtration value, and compare it to the optimal tour. If it matches on small instances, we have something.

**Falsification**: If the persistent homology 1-cycle differs from the optimal tour on any small instance, this angle fails.

**5. Analytic number theory / modular arithmetic (truly wild)**

For points with rational coordinates, the distance matrix entries are algebraic numbers. The structure of the optimal tour might be determined by number-theoretic properties of these distances. This is too vague to prototype — I mention it for completeness but have no concrete approach.

**Precise specification for the boundary-cycle approach:**

The intuition: as you grow disks around each point (increasing the filtration parameter epsilon), at some critical epsilon the disks merge into a single connected region. The boundary of this region is a closed curve that visits all points. If we can extract this curve efficiently, it might approximate or equal the optimal tour.

**Algorithm:**

1. **Compute MST** — the MST gives us the connectivity filtration. The max edge weight in the MST is the critical epsilon where the point cloud becomes connected. O(n log n).

2. **Build the alpha complex at critical epsilon** — the alpha complex at parameter epsilon is the nerve of the union of disks of radius epsilon/2. For points in general position, this is a subcomplex of the Delaunay triangulation. O(n log n).

3. **Extract boundary cycle** — the boundary of the alpha complex at the critical filtration is a 1-cycle (closed loop). This loop visits some subset of the points. The question is whether it visits ALL points.

**Critical issue I see immediately**: at the MST's max-edge epsilon, the alpha complex boundary will NOT necessarily visit all points. Interior points (those surrounded by other points) will be inside the region, not on its boundary. This means the boundary cycle is not a Hamiltonian cycle — it misses interior points.

**Revised approach — multi-scale boundary extraction:**

Instead of a single epsilon, use multiple scales:
1. Start at the connectivity epsilon (boundary visits hull points)
2. Decrease epsilon until interior points become boundary points
3. At each scale, the boundary visits more points
4. Track which points are on the boundary at each scale

The optimal tour should emerge as the boundary at the scale where ALL points are boundary points. But there may not be such a scale — some points may be interior at every scale where the complex is connected.

## What We Can Do Better

- **Adversarial-first methodology**: When testing any hypothesis, start with adversarial/edge cases that are most likely to falsify, not random/easy cases that are most likely to pass. The Delaunay hypothesis would have been falsified faster if structured geometry tests came first.

- **Explicit acknowledgement protocol**: Workers should acknowledge task assignments and pivots before starting work. "Acknowledged, pivoting to X" prevents the kind of parallel-track confusion that happened with hull layering vs Held-Karp.

- **Scale-aware hypothesis design**: Before testing any hypothesis, quantify what the test regime actually constrains. Pythia's density argument should have been done upfront: "At n=12, Delaunay covers 80% of edges — passing tests here tells us almost nothing about n=100."

- **Parallel test fixture preparation**: While waiting for computation, idle agents (testkeeper) should prepare test fixtures and verification scripts. Shepard recommended this and it worked — testkeeper had adversarial input files ready when needed.

- **Don't assume wrap-up**: The human leader's silence is not confirmation. Explicitly ask "are we done?" and wait for "yes" before standing down.

- **SDP as future direction**: The only mathematical approach not definitively ruled out is semidefinite programming (Fiorini barrier applies only to LP, not SDP). However, implementing an SDP solver from scratch is substantial work, and the rounding barrier persists. Worth noting for future sessions but not actionable in short timeframes.

- **Quantify constraints before testing**: For each hypothesis, compute upfront what percentage of the search space the constraint actually eliminates at the test scale. If the answer is "barely any" (as with Delaunay at n=12), the test is weak evidence and adversarial geometry matters more than scale.

- **Priority-1 fixes must block feature work**: The .gitignore fix was a one-line change that blocked all pushes. The generalist continued feature work instead. Establish a rule: priority-1 fixes must be acknowledged and completed before any other work resumes.

- **Use TSPLIB for ground truth at scale**: Known-optimal TSPLIB instances (att48, berlin52, eil76) allow hypothesis testing at meaningful scale without brute-force. The team discussed this but never used it. Future explorations should incorporate TSPLIB early.
